# 出题前端（方案与实施清单）

目标：出题人在网页上完成三件事——上传题目文件、写题面 Markdown、填写 `problem.ts` 的参数——不用手改仓库。

> **实施状态（方案 B，切片 1–3 已完成）**
>
> 落地位置：`lib/problems/library.ts`（运行时快照）、`lib/problems/authoring.ts`（草稿、校验、发布）、
> `lib/problems/statement.tsx`（运行期 MDX）、`app/(site)/admin/problems/`（页面与 Server Action）、
> `app/api/admin/problems/[slug]/files/`（判题文件上传）。
>
> 与本文的偏差，都是上面几节的架构约束逼出来的：
>
> 1. **注册表没有变 async。** `problemBySlug`、`contestProblemRefs`、`problemsServedBy` 仍同步；
>    库中的题目由一个带 `generation` 的进程内快照叠加进来，启动时加载、发布时重载，索引按
>    `generation` 记忆化。B4 的代价（约 40 处同步调用点与它们的测试全部改 async）没有必要付。
> 2. **`ui` 与 preset 由 `content/authoring.ts` 声明**，平台不知道字段名与 preset 语义；
>    题面可用组件由 `content/statements.tsx` 声明。这是两个新的 content 入口。
> 3. **题面不允许 `import` / `export`**：运行期没有打包器，也没有可解析的相对路径。
>    `content/statements.tsx` 就是全部可用组件。
> 4. **`script` 没有默认的 `run.sh`**：表单从已上传的文件里选，平台不假定文件名。
> 5. **第七节问题 1 的答案**：`proxyClientMaxBodySize` 保持 262144。按 B3，只有判题文件入库，
>    测试数据由脚本按 `${JOB_ID_SHA16}` 现场生成，所以判题文件（KB 级）够用。
> 6. **preset 只提供 `default` 与 `answer-only`**：现有题目的 `views.tsx` 全都是同一个形状，
>    `perf` 会是 `default` 的第二个名字；`interactive` 属于本期不做的后端。
>
> 未做：切片 4 的"导入现有题目"；B6 切片 1 的验收（"库里放一道题能在线判"）需要真实
> Postgres 与评测机，本机没有，只做了静态与单元层面的验证。

## 一、先说约束：题目是**构建期**的文件系统内容

`content/_globs.ts` 在模块加载时 eager glob 出所有题目，`problem.ts` 里的 `buildRegistry()` 也是模块级执行，
所以题目是在 `next build` 时进 server bundle 的。四条第 1 类不变式由测试兜着，任何出题路径都必须满足：

| 不变式 | 在哪兜 |
|---|---|
| slug 必须等于目录名 | `content/problems` 的注册表构建 |
| **每道题都必须被某场比赛列出** | `lib/contests/registry.ts:38`（否则直接抛）|
| 每个声明的 backend 必须有题在路由它 | `content/deployment.test.ts:54` |
| `code/**` 逐字节往返、无 CR、makefile 的 recipe 用真 Tab | `content/_shared/judge-files.test.ts` |

由此推出：**"填完表单立刻生效"需要把题目从构建期搬到运行期**，这是一个架构改动，不是一个页面。

## 二、三种做法

| | 机制 | 代价 | 适合 |
|---|---|---|---|
| **A. dev-only 写文件工具** | 表单 POST 到一个仅 dev 的路由，用 `fs` 写出 `content/problems/<slug>/{problem.ts,statement.mdx,views.tsx,code/**}`；提交后回显上面那几条测试的结果 | 只在有仓库的开发机上可用；改完仍需构建/提交 | 少数出题人，先做这个 |
| **B. 题目入库 + 运行时注册表** | 新建表存题目源码；`problemBySlug` 改为从库里读。判题机那条路本来就把 `problem.config` 发过去，所以"库里的题能被判"是现成机制 | 构建期→运行期：注册表、缓存、client-bundle 检查、部署测试、MDX 渲染全要改 | 平台上多人在线出题、改完即时可判 |
| **C. 生成题包** | 表单产出 zip（含填好的 `problem.ts` 与文件），出题人自己提交 | 零架构改动 | 想马上能用又不改架构 |

**建议**：先做 A，并在 A 里顺手提供"导出题包"（C 的能力），这样即使出题人不在开发机上也能用。

## 三、A 的最小实施清单

页面：`app/(site)/admin/problems/new/page.tsx`（放在现有 `/admin` 下，复用控制台外壳）。
写入路由：`app/(site)/admin/problems/new/actions.ts`（server action，**必须** `if (process.env.NODE_ENV === "production") throw`）。

表单字段（对应 `ProblemConfigInput` / `ProblemUi`）：

- 基本：`slug`（lowercase-dash，且 `content/problems/<slug>` 不存在）、`title`、`maxScore`、`difficulty`、`tags`、`languages`、`placeholder`
- backend：`id`（`interactive` / `common` / `leaky-bucket`）+ `script` / `contestant` / `memoryLimitMb` / `maxFileMb`（`common`）或 `makefile`（`interactive`）
- `cases[]`：可增删的表格，列出 `name` / `argv` / `threads` / `timeLimitMs` / `maxScore`；`${JOB_ID_SHA16}`、`argv` 占位符给插入按钮
- `common` 的其余旋钮：`shell` / `stackLimitMb` / `addressSpace` / `seed` / `result.required`。**表单必须是判题机字段的全集**：仓库题目的 `config` 写在 `problem.ts` 里，缺字段随时补；在线出的题目没有文件，表单是它触到 `config` 的唯一入口，漏一个字段就等于那一类题出不了。留空即缺席，让判题机用自己的默认值，别把默认值抄进行里
- 归属比赛：下拉选择要加入哪场比赛的 `problems[]`（不选就构建失败，见不变式 2）
- 题面：MDX 文本域 + 预览
- 文件：拖入 `code/**`

实现要点：

1. **任意扩展名都能传**：`next.config.ts` 里那条 turbopack 规则是按**路径**匹配 `**/code/**` 的，所以 testdata 是什么后缀都行，不需要维护扩展名表。
2. **二进制走 base64**：沿用 `content/_shared/judge-files.ts` 里的 `foi-judge-file:base64:` 约定（Turbopack 的 `source` 已经过文本解码，非 UTF-8 字节会变成 U+FFFD，必须在 loader 里按 `resourcePath` 读原始字节）。
3. **写文件后立刻校验**：直接调 `content/_shared/judge-files.test.ts` 的同一批断言 + slug/归属检查，把结果回显；**不要另写一套校验**。
4. **题面预览复用同一套 MDX 管线**（`Callout` / `Constraints` / `Sample` / `SubmitPanel` + KaTeX 已配好）。预览与线上不一致是这块最容易出的错。
5. **文件大小**：平台当前 `proxyClientMaxBodySize: 262144`（256 KiB），传测试数据会被拒 → 要么调大，要么做分片/直传。
6. **绝不接受**密钥、`.env`、软链接等写进 `code/`——判题机里那些文件是任意代码执行。

## 四、权限（用现成的策略系统，别加角色字段）

- `lib/authz/actions.ts` 里新增动作，例如 `problem.author`（带 `describe`，供控制台渲染）
- `content/policies/staff.ts` 里加一条策略把该动作给相应的人（现有写法：`action: ["admin.enter", "judge.readBoard"]`）
- 页面与 server action 都走 `allows("problem.author", null, viewer)`；控制台的策略矩阵会自动带上它

## 五、方案 B 的实施计划（已定：题目入库 + 运行时注册，只有管理员可出题）

### B0. 本期范围：只做 `common`（已定）

表单里**不提供 backend 选择器**，`backend_id` 固定为 `common`。这砍掉了大半复杂度：

- **没有编译流程要建模** —— `common` 的判题逻辑全在那段 `sh` 脚本里，表单只需要收：`script`（脚本名）、
  `contestant`（选手提交替换掉的那个文件），以及脚本要用的其它文件（driver / checker / gen / 小模板）
- **不涉及 makefile**，也不涉及 `interactive` 那套打包器机制（`next.config.ts` 里 `**/code/**` 的 turbopack
  规则与 `tools/judge-file-loader.cjs`）—— `common` 的文件随 `problem.config` 直接发给判题机，与打包器无关
- 判题文件**仍要过 base64 / 文本往返校验**（它们要发给判题机），但"makefile 用真 Tab"这类
  `interactive` 专属断言不适用
- 表单字段收敛为：`script`、`contestant`、`cases[]`（name / argv / threads / timeLimitMs / maxScore）、
  `memoryLimitMb`、`maxFileMb`、`shell`（默认 `sh`，通常不用改），再加题目级的 `maxScore` 与展示 preset

**表单必须内置的两块帮助**（`common` 出题最容易踩的就是这两个）：

1. **`run.sh` 起手模板**：逐个跑测试点、把期望值**当场算出来**（而不是下发答案文件）、最后打
   `FOI_RESULT` 那一行；含 `ulimit`、`set -u`、以及"编译只做一次"的写法（判题机让所有测试点共用
   同一个沙箱目录，所以第一个测试点编译、后面复用）
2. **反作弊提醒**：别把答案留在选手能读到的磁盘上 —— 判题机里选手程序与判题文件**同目录、同 uid**，
   读 `tests/*.out` 直接输出就能满分（a-plus-b 上实测过）；正确做法是脚本自己算期望值，或让数据
   按隐藏种子现场生成（LU 的 `gen.cpp` + `${JOB_ID_SHA16}`）

### B0b. 出题人的操作面：三步（这是 UX 契约）

表单按这三步组织，除此之外的每一项都给默认值，不要求出题人理解：

1. **上传 `code/` 文件夹** —— 拖整个文件夹进来，**保留相对路径**（`run.sh`、`tests/1.in` …），它们就是发给
   判题机的 `files[].path`。二进制/非 UTF-8 文件自动转 base64，出题人不用管编码
2. **填参数** —— 一部分用**下拉从已上传的文件里选**，不让人手打文件名：`script`（默认认 `run.sh`）、
   `contestant`（选手提交替换哪个文件）；其余是 slug / title / 分值 / 难度 / tags / 语言 / placeholder、
   `cases[]`（可增删表格）、`memoryLimitMb`、`maxFileMb`；**归属比赛必填**（对应 `problem_contests`，
   见 B2b）。展示 preset 收在"高级"里，默认 `default`，不填也能用
3. **题面 markdown** —— 一个编辑区 + 实时预览，可用组件限定为 `Callout` / `Constraints` / `Sample` /
   `SubmitPanel` / `CodeInput` 与 KaTeX；预览必须复用站点同一套 MDX 管线

提交之后系统自动做（出题人不用记）：

- 落库为 `draft`，然后跑校验：slug 唯一、每个文件往返一致、归属比赛存在、题面 MDX 能编译
- 校验过了才允许"发布"；发布时写 `problem_contests` 的 `position`（按选择的顺序）

### B1. 数据模型

- `problems`：slug（唯一索引）、title、statement_mdx、max_score、difficulty、tags、languages、placeholder、
  backend_id（**本期固定 `common`**，留着这一列是为了以后加别的评测机时改数据而不是改表）、
  config(jsonb)、views_preset、views_params(jsonb)、status（`draft` / `published`）、created_by、时间戳
- `problem_files`：problem_id、path、content、encoding、size —— **只放判题文件**（run.sh / makefile /
  driver / checker / gen，KB 级），见 B3
- `problem_contests`：problem_id、contest_slug、label（可空）、position —— 归属关系，以及比赛页里的显示名与
  顺序（对应 `contest.ts` 里 `problems: [{ slug, label? }]` 的数组顺序），见 B2 与 B2b

### B2. 四条不变式怎么处置

| 不变式 | 处置 |
|---|---|
| slug == 目录名 | 文件系统题目保留；库题目没有目录，改成"slug 全局唯一"（唯一索引）|
| **每道题必须被某场比赛列出** | 比赛仍是文件系统内容（`content/contests/*/contest.ts`），而**运行期改不了它**（部署后的镜像是只读的，改文件还要重新构建，与"即时生效"矛盾）→ 所以库题目的归属只存 `problem_contests`，注册表在构建题目↔比赛的映射时把它**按 position 合并**进那些比赛的 `problems[]`；**发布时强制至少选一场比赛**，并校验 slug 存在、比赛窗口未结束（可警告）|
| 每个 backend 必须有题路由 | 变成运行时检查（库里可能有、CI 里没有）→ CI 只校验文件系统部分，库题目在"发布"那一步校验 |
| `code/**` 逐字节往返 | 库题目不经过打包器 → 改成**上架时**对每个文件做同样的往返校验 |

`test/check-client-bundle.ts` 与 turbopack 的 `**/code/**` 规则只对文件系统题目有意义（库题目的文件随
`problem.config` 发给判题机）→ 检查范围要收窄。

### B2b. 归属是"两个来源合并"，页面必须照此实现

出题表单里那个"这道题属于哪场比赛"是**必填**的（否则踩上面第二条不变式），但它写的是 `problem_contests` 一行，
**不是** `contest.ts`：

- 比赛页 / 目录页列题目时：文件系统的 `problems[]` **加上** `problem_contests` 里属于它的行（按 `position` 排，
  `label` 覆盖显示名）
- "把库题目加进另一场比赛" = 插一行 ✓；"从比赛里移除" = 删一行 ✓ —— 都不需要改文件、不需要重新构建
- 文件系统题目仍然只能靠改 `contest.ts` 调整归属；两条路并存是刻意的，不做大迁移
- 所以**切片 1 就要把 `problem_contests` 一起建出来**，否则合并逻辑要多一次迁移

### B3. 测试数据不入库（重要）

`files[]` 会整包发给判题机，所以：

- **判题文件**（脚本 / makefile / driver / checker / gen）入库 ✓ —— 它们本来就是 KB 级、且必须随配置走
- **测试数据**（MB～GB 级）**不要入库** ✗ —— 推荐"脚本按隐藏种子现场生成"：LU 那道题的 `gen.cpp` +
  `${JOB_ID_SHA16}` 就是这个模式。否则等于往 Postgres 里塞几百 MB 二进制，每次领活都要读一遍

### B4. 注册表从构建期改到运行期（这才是 B 的成本所在）

`buildRegistry()` 现在是模块级**同步**执行 → 要变成"运行时可读 + 带缓存"：

- `problemBySlug` 变 async（库 + 文件系统合并），用 React `cache` / `unstable_cache` 缓存，管理端发布时
  `revalidatePath`
- **所有消费方都要跟着改成 async**：题目页、比赛页、榜单、submission 页 —— 工作量大头在这里，不在表单
- 文件系统题目**保持不变**（共存，不做大迁移）；管理端可选提供"把现有题目导入库"

### B5. 权限（按你的要求：只有管理员）

- `lib/authz/actions.ts` 新增 `problem.author`（带 `describe`，供控制台渲染）
- `content/policies/staff.ts` 里把该动作给现在持有 `admin.enter` 的那批策略 → 这就是"只有管理员"
- 页面与 server action 都走 `allows("problem.author", null, viewer)`

### B6. 切片顺序（每片都能独立验收）

1. 表 + 迁移 + `problemBySlug` 读库（**只读**，先不给出题 UI）→ 验收：现有测试全绿，库里放一道题能在线判
2. 草稿态 + 运行时校验（slug 唯一、往返、归属）→ 验收：一条坏数据只影响它自己，不带崩构建
3. 管理端表单：参数 + 判题文件上传 + 题面 MDX 预览（复用现有 MDX 管线）
4. 发布流程；可选："导入现有题目"

## 六、展示层：只允许选内置组件（已定）

出题人**不能**写 `views.tsx`，只能从内置展示组件里选一个 preset。

- 数据：`problems.views_preset`（text，默认 `default`）+ 可选 `views_params`（jsonb，给需要少量参数的 preset）
- 解析：`viewsFor(slug)` 从库里读 preset 并返回**内置模块**；没有值时退回 `default`，所以不填也能用
- preset 清单（按现有题目的真实形态归纳，对应现在每道题 `views.tsx` 导出的那几个位置）：

  | preset | 形态 | 现有例子 |
  |---|---|---|
  | `default` | 代码提交 + 测试点表格 + verdict 文本 | a-plus-b、lu |
  | `perf` | 在上面的基础上显示耗时/成绩与满分成绩的对比 | sssp-hpc、openmpi-pi |
  | `interactive` | 题目自带 driver 的交互形态 | interactive 那批 |
  | `answer-only` | 只有提交框与状态，不展示测试点细节 | vadd（只看正确性）|

- 理由有两层：
  1. **风格与一致性由代码评审保证** —— 不会出现每题一套展示、随出题人漂移；
  2. 题面是 MDX，而 MDX 本身支持 `import`/`export`，所以"出题人写的代码会不会在站点里执行"这件事
     在题面上本来就存在。只有管理员能出题，风险等级等同于改代码库本身，因此题面允许用现成的
     `Callout` / `Constraints` / `Sample` / `SubmitPanel` / `CodeInput` 与 KaTeX，但**不再提供**额外的
     自定义组件注册入口。
